# Augmentation of SLM Risk Assessment with Explainable Social Engineering Detection Evidence

## 1. Project Overview

This project develops an AI-powered **social engineering detection system** that analyses messages for malicious intent and identifies the social engineering techniques present within them.

The system combines a transformer-based detection model, multi-label technique classification, explainable AI (XAI), evidence construction, and small language model (SLM) risk assessment. The main research focus is whether explainable evidence produced by the detection system can improve the quality of risk assessments generated by a small language model.

The project is implemented primarily as a local research prototype, allowing the detection and risk-assessment pipeline to be run without relying on external APIs for the core inference process.

---

## 2. Research Aim

The project investigates whether **explainable social engineering detection evidence can augment and improve risk assessment performed by a small language model**.

The experiment compares SLM risk assessments made:

1. Without detection evidence.
2. With baseline detection evidence.
3. With evidence generated by the transformer-based detection system.

The goal is to determine whether providing interpretable model evidence leads to better-quality and better-justified risk assessments.

## 3. Development Methodology

### Data Collection

Publicly available datasets containing benign and malicious messages were combined to create the project dataset.

The final enriched dataset contains just under 51,000 messages and is approximately balanced between benign and malicious examples for the binary classification task.

### PII Masking & Data Cleaning

Potentially identifying information was masked using placeholders before downstream processing.

The dataset was also cleaned to remove malformed, unsuitable, and otherwise problematic records.

### Technique Annotation

Messages were annotated with the social engineering techniques represented in their content.

The project uses ten technique categories:

- Urgency
- Authority
- Fear
- Reciprocity
- Curiosity
- Pretexting
- Promotional
- Transactional
- Reminder
- Personal

The task is multi-label because a single message can contain multiple techniques.

### Dataset Enrichment & Deduplication

The datasets were enriched with technique annotations and supporting metadata.

Exact duplicates and highly similar messages were removed to reduce repeated campaign examples and potential data leakage. The resulting dataset was used for both binary malicious-message detection and multi-label technique detection.

### Data Splitting

The dataset is separated into training, validation, and held-out evaluation data.

The training data is approximately balanced between benign and malicious messages, while the evaluation data retains a controlled distribution for assessing model performance.

Technique-level class imbalance is handled during model development rather than simply removing rare techniques from the evaluation data.

### Binary Classification

A transformer-based binary classifier determines whether a message is benign or malicious.

The primary detection model uses **ModernBERT-base** with a classification head and sigmoid probability output.

### Multi-label Technique Classification

A multi-label classifier predicts the social engineering techniques present in each message.

Each technique receives an independent probability, allowing multiple techniques to be detected within the same message.

### Probability Calibration

The binary detection probabilities are calibrated before being used as downstream evidence.

Calibration is intended to make the reported malicious probability more meaningful and suitable for use by the risk-assessment component.

### Explainability

XAI methods are used to identify token-level evidence associated with the model's predictions.

The project explores transformer-compatible approaches including LIME, SHAP, and `transformers-interpret`.

### Evidence Construction

The detection and XAI outputs are converted into a compact evidence representation containing information such as:

- Malicious probability
- Overall risk level
- Important token-level evidence
- Detected social engineering techniques
- Technique probabilities
- Technique-specific evidence where available

The evidence is provided to the SLM as supporting information rather than as ground truth.

### SLM Risk Assessment

A local small language model acts as an AI risk assessor.

It receives the original message and, depending on the experimental condition, detection evidence. It produces a risk assessment using four levels:

- Low
- Moderate
- High
- Critical

The SLM is instructed to use the evidence to support, challenge, or refine its reasoning rather than blindly reproducing the detector's predictions.

### Experimental Conditions

The primary experimental conditions are:

| Condition | Description |
|---|---|
| **No Evidence** | The SLM assesses the original message without detector-generated evidence. |
| **Baseline Evidence** | The SLM receives evidence from a baseline detection/evidence pipeline. |
| **BERT Evidence** | The SLM receives evidence generated by the transformer-based detection and XAI pipeline. |

The same underlying messages and risk-assessment task are used across conditions to make the comparison as controlled as possible.

### Evaluation

Risk-assessment outputs are evaluated using **Prometheus 2**, an independent language-model-based evaluator.

The evaluator scores the quality of the generated assessments using a predefined evaluation rubric covering aspects such as relevance, reasoning, and justification.

## 5. Detection Model

The primary malicious-message detector is based on **`answerdotai/ModernBERT-base`**.

The model:

- Encodes the input message using ModernBERT.
- Produces a pooled representation.
- Applies dropout and a classification head.
- Produces a maliciousness logit.
- Converts the logit into a probability using sigmoid activation.
- Applies post-hoc probability calibration.

The detector is responsible for determining the likelihood that a message is malicious. Its output subsequently becomes part of the evidence supplied to the risk-assessment stage.

---

## 6. Technique Detection

The system additionally identifies the social engineering techniques represented in a message.

The current taxonomy contains:

| Technique | General meaning |
|---|---|
| **Urgency** | Pressure to act quickly or before a deadline. |
| **Authority** | Use of a claimed authority, organisation, or official role to influence the recipient. |
| **Fear** | Threats or consequences intended to create anxiety or compliance. |
| **Reciprocity** | Creating an expectation that the recipient should return a favour or benefit. |
| **Curiosity** | Encouraging interaction by exploiting interest or mystery. |
| **Pretexting** | Constructing a deceptive scenario or identity to make a request appear legitimate. |
| **Promotional** | Use of offers, rewards, discounts, or promotional framing. |
| **Transactional** | Goal-oriented communication designed to prompt an action such as a transfer, click, or disclosure, often presented as a routine task. |
| **Reminder** | Presenting a communication as a reminder, notification, or expected obligation. |
| **Personal** | Using personal or relationship-oriented context to make a message appear familiar or trustworthy. |

Because techniques are not mutually exclusive, the model performs multi-label classification.

---

## 7. XAI & Evidence Generation

The XAI component converts model predictions into evidence that can be interpreted by the downstream SLM.

The evidence-generation process combines:

- Calibrated maliciousness probability.
- Predicted risk level.
- Token-level attribution.
- Technique probabilities.
- Technique-specific token evidence.

Where a technique has no prominent supporting evidence, the output can indicate that no prominent evidence was detected rather than forcing an explanation.

The evidence is intentionally presented as **model-derived supporting information**, not as definitive proof of malicious intent.

---

## 8. SLM Risk Assessment

The SLM acts as a lightweight AI risk analyst.

It receives the original message and, for evidence-based conditions, the output of the detection system.

The risk assessor is instructed to:

- Consider the message itself.
- Use supplied detection evidence as supporting information.
- Treat probabilities as model associations rather than proof.
- Avoid inventing external facts.
- Avoid assuming hidden attacker motives.
- Represent uncertainty where the message is ambiguous.
- Produce an overall risk assessment and justification.

The project currently uses local SLM inference so that the risk-assessment experiment can be reproduced without requiring an external LLM API.

---

## 9. Evaluation Methodology

The project evaluates both the underlying detection system and the downstream risk-assessment experiment.

### Detection Evaluation

The classification components are evaluated using standard classification and calibration metrics, including:

- Precision
- Recall
- F1-score
- ROC-AUC
- PR-AUC
- Brier score
- Log loss
- Reliability analysis

### Risk-Assessment Evaluation

The SLM is evaluated under each experimental condition using a held-out set of messages.

**Prometheus 2** is used as the independent evaluator. It assesses the generated risk assessments using a consistent rubric rather than simply checking whether the SLM agrees with the supplied detector evidence.

---

## 10. Statistical Analysis

The scores produced by Prometheus 2 are compared across the experimental conditions.

The analysis considers:

- Descriptive statistics
- Score distributions
- Differences between conditions
- Confidence intervals
- Statistical significance
- Effect sizes where appropriate

Because the same messages can be evaluated under multiple conditions, the analysis accounts for the paired structure of the experiment where appropriate.

## 13. Limitations

The project is a research prototype and has several limitations:

- Public datasets may not fully represent contemporary real-world social engineering.
- Technique annotation can be subjective, particularly where multiple techniques overlap.
- The technique taxonomy does not cover every possible social engineering strategy.
- XAI attribution represents model-associated evidence rather than causal explanations.
- SLM outputs can vary depending on model, prompt, and inference settings.
- Prometheus 2 provides model-based evaluation rather than human ground truth.
- The evaluation is limited in scale by available time and computational resources.
- The system should not be treated as a production security control without further validation.

## Usage

The exact commands may vary with the final repository structure. The intended workflow is:

### 1. Prepare the Dataset

Run the data preparation pipeline to:

1. Load the source datasets.
2. Mask PII.
3. Clean and normalise messages.
4. Apply technique annotations.
5. Enrich the dataset.
6. Remove duplicate and highly similar records.
7. Create the required train, validation, and evaluation splits.

### 2. Train the Detection Models

Train the binary malicious-message detector and multi-label technique classifier.

```bash
python <training-script>.py
```

Model checkpoints should be stored in the project's designated model directory.

### 3. Calibrate Probabilities

Run the calibration pipeline using the appropriate validation data.

```bash
python <calibration-script>.py
```

The resulting calibration parameters are then used when generating detection evidence.

### 4. Generate XAI Evidence

Run the evidence-generation pipeline against an input message or evaluation dataset.

```bash
python <evidence-script>.py
```

The resulting evidence contains the detector's predictions, technique information, and XAI attribution.

### 5. Run SLM Risk Assessment

Run the local SLM risk assessor using one of the available experimental conditions.

```bash
python <risk-assessment-script>.py
```

The experiment can be configured to use:

```text
no_evidence
baseline_evidence
bert_evidence
```

### 6. Run Evaluation

After generating the SLM assessments, run the Prometheus 2 evaluation pipeline.

```bash
python <evaluation-script>.py
```

The evaluation outputs can then be used for the statistical comparison of the experimental conditions.

> **Note:** The placeholder commands above should be replaced with the final script names and arguments once the repository structure is finalised.

## Reproducibility

For reproducible experimentation:

- Use the provided dependency versions where available.
- Use the specified dataset splits rather than recreating evaluation data.
- Record model checkpoints and calibration parameters used for each experiment.
- Keep SLM model, temperature, prompt, and experimental condition fixed when comparing results.
- Use the same evaluation messages across experimental conditions.
- Preserve the final evaluation outputs used for statistical analysis.
